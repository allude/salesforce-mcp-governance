# 🔐 Zero-Trust Security Model & Threat Mitigations

This document describes the security controls in the **Streamable HTTP MCP runtime (`/mcp`)** and the **Admin Control Plane (Next.js portal + `/api/admin/*`)**, with pointers to the code that implements each one.

---

## 1. Zero Shared Service Accounts on `/mcp`

* **Threat:** a single integration-user token on the backend lets any Copilot user (or a prompt injection) read or change data that user could never see.
* **Mitigation:** `/mcp` never uses a shared token. Every request must carry the end user's own Salesforce `Authorization: Bearer <token>`, and every Salesforce call is made with that token, so Salesforce still enforces sharing rules, object CRUD and field-level security for that user.
* **Verification:** `resolveSalesforceUserFromToken()` in [`src/salesforce/client.ts`](../src/salesforce/client.ts) validates the token against `/services/oauth2/userinfo` and then reads `SELECT Id, Username, Name, Email, ProfileId, Profile.Name FROM User WHERE Id = '<userId>'` with the same token.
* **Safe caching:** the verified identity (never the token) is cached for 120 seconds under a SHA-256 digest of the token (`hashToken()`), capped at 5,000 entries. Raw tokens are never written to disk or to the audit log.
* **Challenge, not redirect:** without a valid token, `/mcp` returns `401` with an RFC 9728 `WWW-Authenticate` header ([`src/mcp/streamableHttp.ts`](../src/mcp/streamableHttp.ts)). Reflected error text is reduced to printable ASCII so a crafted token can never break the header or crash the process, and every async handler passes failures to Express's error handler.

## 2. Profile → Access Group → Tool / Object / Field Enforcement

Implemented in [`src/rbac/policyEngine.ts`](../src/rbac/policyEngine.ts) and [`src/mcp/server.ts`](../src/mcp/server.ts).

* **Default deny.** A caller whose Salesforce Profile is not registered in **Salesforce > Profiles**, or has no Access Groups, sees no tools and every call is denied.
* **Profile matching.** The caller's `ProfileId` (from the `User` lookup) is matched to registered Profiles by ID, treating the 15- and 18-character forms of the same ID as equal. If no ID matches, the Profile name is used as a fallback. If the `User`/`Profile` lookup itself fails (e.g. the token lacks the `api` scope), the caller gets no Profile at all, so no tools; the server never guesses one.
* **Effective permissions** are the union of the Profile's groups: allowed MCP actions, per-object `canRead` / `canCreate` / `canUpdate` / `canDelete`, and allowed fields, intersected with the Objects and Fields enabled globally in **Salesforce > Objects**. A flag grants only when it is exactly `true`: a stored `"false"`, `1` or `null` never counts as granted. An object entry that grants no CRUD flag contributes nothing (not even its fields). A stored entry the engine cannot read (not an object, an `objectName` that is not text, a flag that is not `true` or `false`, or `allowedFields` that is not a list of names) is skipped whole and grants nothing; it never makes evaluation fail. It is logged once per group, entry and reason, by key and never by value, and listed in the evaluation's `skippedGroupEntries`. A group column that does not parse reads as an empty list. The portal's summaries of stored groups (a Profile's effective access, the Profile ↔ Group matrix, an Object's "Used by groups") read entries the same way, so they never show access `/mcp` does not give. `POST /api/admin/groups` stores only checked grants, under the catalog's spelling of each Object and field, with the entries for one Object merged; so such entries come only from groups saved by an older version. On upgrade, a one-time migration rewrote stored grants to the catalog's spelling and merged entries that name one Object in different cases, which the engine had already matched case-insensitively. It left the entries of an Object the catalog held under more than one spelling (an older version could store `Opportunity` and `opportunity` as two rows) as they were: the engine reads whichever of those rows is enabled, so a merge could have judged an entry by another row's fields. A merged entry gives what its entries gave one by one, including the `Id` of an entry that names none of the Object's fields (see the next rule), which it lists outright. The one exception no stored list can avoid: an entry whose fields all exist but are disabled gives `Id` only while they stay disabled, and merged with an entry that names an enabled field it no longer does, so merging can only narrow access, never widen it. An entry that grants Read, Create or Update but lists no field that is enabled globally (none at all, or only disabled or unknown ones) contributes `Id`, when `Id` is enabled, whatever the Profile's other groups grant. Both rules look at each entry on its own, so the result never depends on the order of groups. Deleting an Object removes it from every group, so re-importing it cannot silently restore access. That revocation, by the Admin API or an org sync, takes the Object (or the field, from an `allowedFields` list) from every entry that names the Object as text, entries the engine skips included: those grant nothing here, but an older release run on the database after a rollback reads one such as `"canRead": "false"` as a grant, and its own revocation removed them, so after a delete and a re-import the rollback cannot restore that access either. Any other entry the engine skips, and a column that does not parse, is left exactly as stored (never deleted or rewritten, so it stays recoverable by hand). The revocation's audit entry and the sync preview's list of affected groups read entries as the engine does, so an entry it skips names no group. Profile → Group mappings change one membership at a time, so a stale portal tab cannot re-grant a group removed elsewhere; a full replacement must name the groups it was built from and is refused (`409`) if they changed. Likewise a group carries a `version`, and the portal's group editor saves with the version it loaded: a group changed elsewhere since (including a grant revoked by deleting its Object or field, and a change an older release run on the database after a rollback made, which a trigger stored in the database gives a new version) is refused (`409`) rather than overwritten. A save that changes nothing writes nothing and keeps the version, so it never makes another editor's draft stale; it is still logged, with an empty diff. Every change is atomic, and unknown group IDs are rejected before anything changes.
* **Discovery-time filtering:** `getVisibleToolsForUser()` limits `tools/list` to the granted actions.
* **Execution-time enforcement: the decision pipeline.** Every `tools/call` is decided by `evaluatePolicy()` before anything is sent to Salesforce. It decides from a policy snapshot alone (`loadPolicySnapshot()`: the Profiles, the Access Groups, the mappings, the Object and field catalog with its enabled and missing-in-org flags, and the [policy revision](api-and-tools-reference.md#policy-revision)), read once per call; the handler then acts on that same snapshot, so a change saved mid-call cannot split one call between two policies. It reads nothing else and never throws. Its result, the decision, holds:
  * `outcome` (`allowed`, `denied`, `invalid` or `error`), a `code`, and the `reason` the caller is given;
  * `steps`: one per stage reached, in order, each `pass` or `fail`, with `grantingGroupIds` (the assigned groups that grant what the step checked: the tool, the Object, the operation, the fields named; empty for a failed step), the step's `objectName` and `fieldNames` (those requested on a pass, those refused on a fail), and a `ruleId` kept for row filters (always `null` for now). Nothing after the failing step is recorded. An allowed decision made with the call's arguments ends on an `input` pass, which says its arguments were checked and passed; a check made without them (`evaluateMcpToolCall()`, the simulator without a sample payload) has none, so the two cannot be mistaken for each other;
  * `assignedGroups` (every group mapped to the Profile), `decidingGroupIds` (for an allowed call, the groups the passing `tool_grant`, `object`, `crud` and `fields` steps name, so a call whose tool comes from one group and whose Object access from another names both; otherwise empty), `identity` (`callerProfileId`, `matchedProfileId`, and `matchMethod` `id`, `name` for the Profile name fallback, or `none`), `policyRevision`, and `skippedGroupEntries` when a stored entry was skipped.

  The stages, in the order they run, and the code a failure gives:

  | Stage | Passes when | Code on failure |
  | :--- | :--- | :--- |
  | `tool` | the tool is a catalog tool (an unknown name is refused even if a group lists it) | `TOOL_UNKNOWN` |
  | `identity` | the caller's Profile is registered (matched by ID, else by name) | `PROFILE_UNREGISTERED` |
  | `groups` | the Profile has at least one Access Group | `NO_GROUPS` |
  | `tool_grant` | one of those groups grants the tool | `TOOL_NOT_GRANTED` |
  | `object` | object-scoped tools only: the named Object is enabled in **Salesforce > Objects** and granted by a group | `OBJECT_NOT_GRANTED`; `OBJECT_BLOCKED` when a group grants it but it is disabled or not listed in **Salesforce > Objects** |
  | `crud` | a group grants the operation's CRUD flag on it | `CRUD_MISSING` |
  | `fields` | every field the call selects or writes is in the allowlist | `FIELD_NOT_PERMITTED` |
  | `where` | `soql_query`'s `whereClause` names only allowed fields | `WHERE_FIELD_NOT_PERMITTED` |

  `list_enabled_objects` names no Object, so its access stages end at `tool_grant` and an `objectName` sent with it is ignored. Malformed arguments fail an `input` step with `INPUT_INVALID`. They are checked where the handlers always checked them, so a call with two problems is told about the same one as before: a missing `objectName` before the Object is looked up; in `object`, an `objectName` that names no granted Object and is not text or not an API name (`ACCT-99812`, `Account WHERE ...`, `42`), which gets the reason an ungranted Object gets; after `crud`, the `recordId` of `get_record`, `update_record` and `delete_record`, then the `fields` map of `create_record` and `update_record`, then the `fields` list of `soql_query` and `get_record`, any of whose names cannot be read as text; and inside `where`, a clause the guard cannot read (over 2,000 characters, a character outside its grammar, unbalanced parentheses). Access is always decided first, so a caller learns nothing about its arguments from an Object it may not use. An Object the catalog holds under a name that is not an API name (stored before names were validated) is a fault in the policy, not in the caller's arguments: after `crud` the decision is `error` (`INTERNAL_ERROR`) with the reason `Object '<name>' is not a valid Salesforce API name.`, and no step fails. `ROW_FILTER` is reserved for row filters and not given yet.
* **Outcomes and logging.** `allowed` runs the call. A permission failure is `denied` with its code. A problem with the caller's arguments is `invalid` (`INPUT_INVALID`) and is logged as `DENIED`, not `ERROR` (owner decision D12): the call was refused, nothing failed. An exception inside the evaluation, or an Object stored under a name that is not an API name, is `error` (`INTERNAL_ERROR`), is logged as `ERROR`, and allows nothing. What the caller receives did not change when these checks moved into the pipeline: a refused tool or Object (a missing or malformed `objectName` included) gets the `ACCESS_DENIED` payload naming the Profile, a refused field or filter the `ACCESS_DENIED` payload without it, and a malformed argument or an `error` decision a plain `{ "error": "<message>" }`, each with the same text as before (see the [API reference](api-and-tools-reference.md#denial-response-format)). Each `tools/call` still writes one log row; one whose params the MCP SDK refuses (`arguments` that is not an object, a `name` that is not text) is answered with a JSON-RPC error before the handler runs, so it is neither decided nor logged. `evaluateMcpToolCall()` keeps its result shape (`permitted`, `reason`, `matchedGroups` listing every assigned group, `allowedFields`, `objectName`) and adds the `decision`; like the simulator without a sample payload, it checks the tool and Object stages only.
* **Field and filter allowlists:** the pipeline refuses any requested or written field outside the allowed set: the `fields` list of `soql_query` and `get_record`, and the field names `create_record` and `update_record` write. Responses are not filtered: the records Salesforce returns are passed back as they arrive, so the allowlist limits what a call asks Salesforce for, not what comes back. A `soql_query` or `get_record` left with no field to select (an empty `fields` list, or only fields missing from the org) selects `Id`. `soql_query`'s `whereClause` is tokenised by [`src/mcp/soqlGuard.ts`](../src/mcp/soqlGuard.ts) and may only reference allowed fields, `Id` and literals. Subqueries, relationship paths, bind variables and other syntax are refused, so a filter cannot be used to probe a hidden field or another object. `recordId` must be a 15/18-character ID before it goes into a URL path. Object and field names must be plain Salesforce API names (`Account`, `Amount__c`): the SFDX importer skips anything else, `POST /api/admin/objects` rejects it, and the pipeline re-checks every name before the handler puts it into SOQL or a REST path (the handler checks the Object name once more), so crafted metadata cannot smuggle a subquery or relationship path into a query. Query limits are capped at 200 rows.
* **Logging:** a refused call is returned as an MCP tool error and logged as `DENIED`, whether a permission or the caller's arguments refused it; a Salesforce failure, or a policy that could not be evaluated (a stored Object name that is not an API name included), is logged as `ERROR`.
* **Policy revision.** `policy_state` holds one counter that goes up by one with every committed transaction that changes a Profile, Object, field, Access Group or mapping, and with nothing else (see the [API reference](api-and-tools-reference.md#policy-revision)). Triggers the server adds to its own connection raise it inside the transaction that makes the change, whichever code path or cascade it comes from, so a committed change the server makes is never visible without its new revision and a rolled-back one never raises it. A change written through any other connection, such as an older release run on the database after a rollback or a hand edit, does not fire those triggers. Triggers stored in the database tally it instead, on every connection, and the server counts whatever was tallied as one revision when it next starts, before it serves a request, so the changes an older release made get a revision of their own. A hand edit made while the server runs is in force under the revision it found until the server restarts. Okta, the Salesforce connection and its Org ID lock, certificates, portal users and sessions decide authentication, not the policy, and are not counted.

## 3. Server-Side Request Forgery (SSRF) Protection

* **Threat:** a crafted `X-Salesforce-Instance-Url` header, a mis-set instance URL, or a userinfo response pointing at internal hosts (`http://169.254.169.254`) or an attacker's server could make the backend send requests, and the user's Bearer token, somewhere else.
* **Mitigation:** `validateSalesforceInstanceUrl()` in [`src/salesforce/client.ts`](../src/salesforce/client.ts) runs on every URL before `fetch`: the instance-URL hint, the configured instance URL, and the `custom_domain` / `rest` URLs returned by userinfo. It requires the host to match `SALESFORCE_ALLOWED_DOMAINS` (entries starting with `.` match that domain and its subdomains, so `login.salesforce.com.evil.com` is rejected), requires `https:` in every environment, accepts only plain DNS hostnames (letters, digits, `-` and `.`) on the default port, and rejects URLs with embedded credentials. The authorization server advertised in the `401` challenge and the OAuth metadata goes through the same check, falling back to `SALESFORCE_LOGIN_URL` and then `https://login.salesforce.com`.

## 4. Org ID Lock

When **Reject tokens from other orgs** is on and an expected Org ID is set (**Settings > Portal Login & Okta SSO > Salesforce Connection & Org ID Lock**, or `PUT /api/admin/sf-settings`), tokens from any other Salesforce org are rejected with `401`, including identities that were already cached. 15- and 18-character Org IDs are compared on their 15-character form. A JWT connect that cannot read the connected org's ID from Salesforce (from the token response's identity URL, or else userinfo) is refused, so a connect never skips the lock or records an org it did not confirm.

## 5. Signed Policy-Simulator Tokens

The portal's policy simulator (`POST /api/admin/test-mcp-access`, admins only) issues `sf_sim_<payload>.<signature>` tokens so an admin can exercise `/mcp` as a given Profile. Each token is signed with HMAC-SHA256 under a sub-key derived (HKDF) from `APP_SECRET_KEY` and expires after 15 minutes. Simulated calls never reach Salesforce. They are logged with a `simulated` marker set from the verified token or the route, under the name `simulated:<name>`, so they cannot pass as a real user, and each simulation writes a portal admin log row naming the admin. Unsigned, tampered or expired simulator tokens are rejected. In production the simulator issues no token and `/mcp` rejects every `sf_sim_` token with `401` without verifying it, so a simulated identity is never accepted by a production server.

## 6. Okta OIDC SSO with PKCE (`S256`) & Remote JWKS Verification

Implemented in [`src/security/adminAuth.ts`](../src/security/adminAuth.ts):

1. **PKCE (`S256`) + state + nonce:** `/auth/okta/login` generates a random 32-byte `code_verifier`, its SHA-256 `code_challenge`, and random `state` and `nonce`, stored in a signed, `HttpOnly`, 10-minute cookie.
2. **Callback verification:** `/auth/okta/callback` checks `state` in constant time, exchanges the code with the `code_verifier`, then verifies the `id_token` with Okta's JWKS (`jose.createRemoteJWKSet()`): signature, `iss`, `aud` (client ID) and `exp`. The `nonce` claim is required and compared in constant time.
3. **Required Okta group:** if an admin group is configured (default `MCP-Admins`), the `groups` claim must contain it, or the login is denied and logged as `OKTA_LOGIN_DENIED`.
4. **Errors:** every other callback failure is logged as `OKTA_LOGIN_FAILED` with its details (an error returned by Okta is logged with its text, up to 300 printable characters, only when the callback's `state` matches this browser's login cookie; otherwise it is logged as `invalid_callback` without the text), and the browser is redirected with a fixed error code only (`/?auth_error=state_mismatch` etc.). The portal maps codes to fixed messages, so a crafted link cannot put attacker-chosen text on the login screen.

## 7. Admin Sessions, CSRF, CORS & Rate Limits

* **Session cookie:** admin sessions are `HS256` JWTs in an `HttpOnly`, `SameSite=Lax` cookie (`sf_mcp_admin_session`, `Secure` in production) that expire after 8 hours. A password session stops working as soon as its portal user is deleted.
* **CSRF:** every session embeds a random `csrfToken`. All state-changing Admin API requests except `login` and `logout` require a matching `X-CSRF-Token` header, compared with `timingSafeStringEqual()` (the portal sends it on logout too).
* **CORS:** the Admin API and Okta routes send no CORS headers. The portal reaches them same-origin through the Next.js proxy, so no other origin can read admin responses or the CSRF token. `/mcp` and `/.well-known` allow any origin, but never with credentials.
* **Rate limits** ([`src/index.ts`](../src/index.ts)): `/mcp` allows 120 requests per minute per bearer token, and the Admin API 300 per minute per admin session; requests without a token or session are limited per client IP, so anonymous traffic cannot use up an authenticated caller's allowance. Failed password logins are limited to 60 per 15 minutes per client IP and 20 per 15 minutes per username, and the Okta routes to 60 per 15 minutes per client IP. IPv6 clients are counted per `/64` network, since one host can use every address in it.
* **Rejected `/mcp` tokens** ([`src/index.ts`](../src/index.ts), [`src/salesforce/client.ts`](../src/salesforce/client.ts)): a valid token is never refused because of a counter someone else filled. Every rejected token still gets `401` and an `unverified_caller` log row (`DENIED`, kind `rejected`, stage `auth`, with the code `ORG_LOCK_VIOLATION`, `INSTANCE_NOT_ALLOWED` or `TOKEN_INVALID` from the typed error [`src/salesforce/client.ts`](../src/salesforce/client.ts) threw). The `401` itself is unchanged: the code is in the log only.
  * Where a trusted proxy named the client (`TRUST_PROXY` covers the connecting hop and the request carried `X-Forwarded-For`, so the client IP differs from the connecting address), each client IP may present 30 rejected tokens per minute; after that it gets `429` with `Retry-After` and nothing reaches Salesforce. Only finished answers to tokens that did not verify count (`401`, or the `503` below when Salesforce gave no verdict). A token that verified within the last hour is exempt, so a flood from a shared address does not lock out callers already signed in, and the exemption ends as soon as that token is rejected (for example after the Org ID lock is turned on).
  * Otherwise the connecting address may be the portal proxy, on loopback or on another host or container (`MCP_BACKEND_URL`), which every caller shares, so there is no per-IP limit; it would let anyone lock out every new sign-in. That includes the default `TRUST_PROXY=false` and direct connections to the backend.
  * In every mode, the cost of rejected tokens is bounded: a token Salesforce rejected is remembered for 5 minutes per login host and refused again without another call, a token with anything other than printable ASCII (spaces included) or over 4096 characters is refused without a call, and at most 8 Salesforce verifications run at once with up to 100 waiting. When the queue is full or a wait passes 10 seconds, the caller gets `503` with `Retry-After: 5` (no log row); a token that verified before at the same login host takes priority over new ones. Each Salesforce verification call times out after 10 seconds.
  * When Salesforce gives no verdict (a timeout, a network failure or a connection lost mid-answer, or `5xx` / `429` from userinfo), the caller gets `503` with `Retry-After: 5` instead of `401`, the attempt is logged as a rejected token (`ERROR`, stage `upstream`, code `UPSTREAM_UNAVAILABLE`, so it counts among the errors, not the denials), the token is not remembered as rejected, and a token that verified before keeps its exemption if that host is the one that vouched for it. A failure at any other host (for example one the caller named in `X-Salesforce-Instance-Url`) ends the exemption, as a rejection does, so a caller cannot keep it by choosing a host that never answers.
* **Client IP:** `TRUST_PROXY` defaults to `false`, because the Next.js proxy forwards `X-Forwarded-For` unchanged and a client could otherwise forge it to dodge per-IP limits and falsify audit-log IPs. With the default, every request arriving through the portal has the portal's address, so the per-IP limits (anonymous traffic, failed logins, Okta routes) act as one shared limit and audit logs show the proxy IP. Behind a load balancer or TLS proxy that appends the client address to `X-Forwarded-For`, set `TRUST_PROXY=loopback` (or a hop count / subnet list) to get real client IPs.
* **Headers:** `helmet` sets HSTS, `X-Content-Type-Options`, a deny-by-default Content Security Policy and frame protection. The backend serves no HTML.

## 8. Secrets, Passwords & Fail-Fast Configuration

* **`APP_SECRET_KEY`** ([`src/config.ts`](../src/config.ts)) is the 32-byte key for AES-256-GCM, session JWTs and simulator-token signing. In production the backend refuses to start if it is missing, not 64 hex characters, or a publicly known value (the development fallback or the `.env.example` sample). In development and test it falls back to a deterministic, insecure key and prints a warning.
* **Secrets at rest:** the Okta client secret is stored in `okta_config.client_secret_enc`, encrypted with AES-256-GCM (random 96-bit IV, 128-bit auth tag) by [`src/security/crypto.ts`](../src/security/crypto.ts). The Admin API only ever returns `hasClientSecret`.
* **Portal passwords** are hashed with PBKDF2-SHA512 (100,000 iterations, per-user random 16-byte salt) and verified with `crypto.timingSafeEqual`.
* **Bootstrap admin:** an empty database is seeded with one portal user from `ADMIN_BOOTSTRAP_USERNAME` / `ADMIN_BOOTSTRAP_PASSWORD` (default `admin` / `admin123`). In production the backend refuses to seed a publicly known password (`admin123`, or the old sample `ChangeMeInProd!2026`). It also refuses to start while any existing portal account still uses one (for example a database created by `npm run dev`); setting `ADMIN_BOOTSTRAP_USERNAME` to that account and a strong `ADMIN_BOOTSTRAP_PASSWORD` rotates it at startup.
* **Input hardening:** every async route hands failures to Express's error handler, login rejects non-string credentials with `400`, and the entry process logs (rather than dies on) any unhandled promise rejection.

## 9. Governance Audit Trail (PII Stripped)

* **`mcp_copilot_logs`:** one row per `tools/call` the gateway's handler receives (`ALLOWED`, `DENIED` or `ERROR`; the MCP SDK answers params it refuses itself, and those write none), per rejected token (`unverified_caller`), and per policy simulation, with the Salesforce user, Profile, matched groups, tool, target object and latency. `stripSensitivePayloadData()` in [`src/db/store.ts`](../src/db/store.ts) runs on every payload before it is stored: record arrays become `[REDACTED N RECORDS]`, a `soql` string is reduced to its skeleton by the [`soqlGuard`](../src/mcp/soqlGuard.ts) tokenizer (every literal becomes a typed placeholder such as `<string>`, `<number>` or `<date>`, and text it cannot read becomes `<unparseable soql>`), and any other value except a short list of top-level structural keys (object, tool and field names, limits, IDs) becomes `<REDACTED:type>`. Those keys count only at the top level, so every value in a nested map such as `create_record`'s `fields` is redacted. Keys are caller text too, so one that is not a Salesforce API name, at any level (a field name typed into `fields` included), is stored by its length (`<invalid:len=N>`, numbered `#2`, `#3`, ... when one level holds more than one), as the decision stores such a name. The tool and target object, in their columns and under the payload's top-level tool and object keys, are stored only when they are a catalog tool (or `mcp_authenticate`) and a Salesforce API name (or `*`); anything else is stored as `<invalid:len=N>`. Each row also records its `kind` (`real`, `simulated`, `rejected`), the decision the policy engine made (`decision_json`, with `decision_stage` and `decision_code` beside it), the assigned and deciding group ids, the `policy_revision` it was decided on, the caller's and the matched Profile id and how they matched, and two timings: `verification_ms` for the bearer token check and `total_ms` from the moment `/mcp` received the request, which `latency_ms` repeats. A row written before these columns keeps them empty (`''`, `'[]'` or `NULL`: not recorded), except `kind`, which every boot fills in from the row's other columns.
  * **Names, never values, in `decision_json`:** the decision is rebuilt from its stages, results, group ids, Object and field names, codes and counts by one pure function ([`src/rbac/decisionLog.ts`](../src/rbac/decisionLog.ts)), and its reason text, allowed fields and the call's arguments are never stored. Because a decision's steps echo what the caller sent (an Object name, the fields it asked for, the identifiers in a WHERE clause), an Object or field name is kept only when it is a Salesforce API name that the synced catalog holds, in the catalog's spelling, a group id only when a group has it, and the matched Profile id only when Salesforce > Profiles has it; a caller's Profile id only in the form of a Salesforce id; a skipped entry's reason only when it is one of the engine's fixed texts. Anything else is stored by its length (`<invalid:len=N>`). The catalog, groups and Profiles are checked as the policy snapshot the call was decided on holds them, not as the tables stand when the row is written, so access revoked while a call ran does not erase from its row the group, Object or Profile that allowed it. Each list of field names and the skipped entries are cut at 200, with a count of what was left out, so no request can bloat a row.
  * **Write order:** both log tables have an explicit `seq INTEGER PRIMARY KEY AUTOINCREMENT`, which every reader orders by and pages on, so the order cannot change when the database is vacuumed and a deleted row's place is never reused. A database from before it is rebuilt once, in one transaction, with every row's old rowid as its `seq`, so ids, order and paging cursors already handed out stay valid.
* **`portal_admin_logs`:** every portal login, failed login, logout, Okta login or denial, and every successful mutation, with admin username, auth method, action code, target and client IP. Each row also records its `result` (`SUCCESS`, `FAILED`, `DENIED`), what it changed by a stable id (`target_type`, `target_id`), a `diff_json` of what changed, and a `correlation_id`.
  * **Transactional:** every Admin API route that changes something writes the change and its row in one transaction, so a change whose audit row cannot be written is rolled back (`500`), the policy revision with it, and can never go unlogged: Profiles, Objects and fields, imports, Access Groups and memberships, org sync applies, Okta and Salesforce settings (the Org ID lock included), the JWT certificate, connecting (and the failure it records) and disconnecting, portal users, the policy simulator's two rows and the sample matrix. Network work (the JWT token exchange) and key generation run first, outside the transaction, which holds only the database write. Sign-in and sign-out rows share no transaction, because a session is a cookie, not a stored change. A refused request (`400`, `403`, `404`, `409`) writes no row, except the failures that are logged on purpose (`*_FAILED`, `*_DENIED`).
  * **No secrets in diffs:** a diff holds names, ids and flags only: group definitions and membership ids. Each grant of a group is rebuilt from its object name, four flags and field names as the policy engine reads them, so nothing else stored with it is logged, and text that is not a Salesforce API name is kept by its length only (`<invalid:len=N>`). A group's name and description are cut at 1,000 characters, an update records only what changed, and a diff over 64 KB is replaced by a note of its length, so no request can bloat a log that cannot be cleared. Settings, Okta, org connection and portal user rows keep no diff at all, so a client secret, private key, password or token can never reach `diff_json`.
  * **Correlation ids** are made by the server, one per Admin API request, and returned as `X-Correlation-Id`. A client-sent `X-Correlation-Id` is ignored, so a caller cannot file its rows under another request.
* Neither table can be cleared through the API.

## 10. Known Limitations

* The Profile **name** fallback means a token from another org whose Profile has the same name as a registered one is matched. Its calls still run with that user's own token against their own org. Turn on the **Org ID lock** to reject other orgs entirely.
* Outside production, `POST /api/admin/objects/import-local-folder` reads XML files from any directory the backend process can access. It is admin-only and audit-logged, and production refuses it with `403`.
* `/mcp` accepts JSON-RPC batches (the MCP SDK's transport, up to 100 messages). The token is verified once per HTTP request and the rate limit counts requests, so one batch counts once toward the 120 per minute per token while it can carry up to 100 tool calls. Each call is still decided by the policy and logged on its own.
* Portal users have a stored role, but no route reads it: every portal user, local or Okta, has full access to the Admin API.
* The per-username login limit means anyone can temporarily block password sign-in for a known username (20 failures, 15 minutes). Okta SSO is unaffected.
* Logging out clears the session cookie, but a stolen session JWT stays valid until it expires (8 hours), and changing a portal user's password does not end their existing sessions (deleting the user does). Rotating `APP_SECRET_KEY` invalidates every session.
